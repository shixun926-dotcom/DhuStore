# DhuStore 商品购买流程优化分析

> 版本：V1.0 ｜ 编写日期：2026-10-28
> 范围：从「浏览商品 → 加入购物车 → 结算下单 → 支付完成」全链路
> 对标：淘宝 / 京东 / 拼多多等主流电商平台的通用做法
> 目的：找出流程设计、用户体验、转化效率、功能完整性方面的差异与不足，形成可落地的优化清单

---

## 〇、当前流程全景（现状基线）

本项目购买链路可抽象为六个环节，每个环节的现状如下：

| # | 环节 | 现状实现 | 关键机制 |
|---|---|---|---|
| 1 | 浏览商品 | 首页轮播 / 分类 / 秒杀 / 推荐 → 列表（分类、关键词搜索、分页）→ 详情页 | 无多规格 SKU，销量/库存展示 |
| 2 | 加入购物车 | 详情页「加入购物车」；服务端原子 upsert；数量按库存封顶 | 勾选态存服务端，失效商品分区展示 |
| 3 | 结算试算 | `GET /api/orders/preview` 由后端统一算价（商品金额/运费/优惠/应付） | 与下单共用 `PricingService`，展示价=实付价 |
| 4 | 提交订单 | `POST /api/orders` 幂等下单；条件扣库存防超卖；`submitToken` 防重复 | 支持购物车结算 + 「立即购买」直购两条路径 |
| 5 | 支付 | 创建支付单 → 收银台 → 本地模拟网关回调 → 推进订单状态 | 支付单复用、回调幂等、倒计时关单 |
| 6 | 支付完成 | 状态机推进（待付款→待发货→待收货→已完成），超时自动关单回补库存 | 乐观锁 `WHERE 旧状态` 保证并发安全 |

**已具备的较好设计**（下面对比时不再重复列为不足）：
- 金额只由后端 `PricingService` 计算，试算与下单同源，杜绝前后端价差；
- 下单走 `submitToken` 幂等 + 数据库条件扣库存，并发安全；
- 购物车失效商品（下架/删除/售罄）分区展示、不参与结算，避免整单阻断；
- 订单状态机集中管理，状态迁移用 `WHERE status = 旧值` 条件更新防并发。

## 一、逐环节对比分析

### 环节 1：浏览商品（商品发现与详情）

**主流平台做法**：多规格 SKU（颜色/尺码/版本）独立库存与价格；详情页带评价、问答、店铺信誉、优惠券领取、收藏、降价提醒、千人千面推荐。

**差异点与不足**：

| 编号 | 差异点 | 现状 | 主流做法 | 影响评估 | 优先级 |
|---|---|---|---|---|---|
| 1.1 | 无 SKU 多规格体系 | 一个商品只有单一 `price` + `stock`，无规格维度 | 淘宝/京东商品按 SKU 管理（颜色、尺码、版本），每个 SKU 独立价格库存 | **高**：无法承接服装、数码等需要选规格的品类，直接限制可售卖商品范围 | P1 |
| 1.2 | 无商品评价体系 | 无评价/晒单/好评率 | 京东/淘宝都有评价、晒图、追评，是转化核心信任要素 | **高**：缺少社会证明，转化率与复购率受影响 | P1 |
| 1.3 | 无优惠券领取入口 | 优惠券只在结算页出现 | 详情页有「领券」入口，券是引流与提转化的核心手段 | 中：券的曝光不足，营销能力受限 | P2 |
| 1.4 | 详情描述为纯文本 | `detail` 字段纯文本渲染 | 富文本图文详情 | 中：信息呈现单调，商品卖点表达弱 | P2 |
| 1.5 | 无收藏/降价提醒 | 只能关注「卖家」，不能收藏「商品」 | 商品收藏、降价提醒、到货提醒是标准能力 | 中：流失潜在购买用户，复购抓手缺失 | P2 |
| 1.6 | 推荐逻辑简单 | 「相关推荐」= 同分类随机/列表取前几个 | 千人千面、协同过滤、购买后推荐 | 低：当前体量可接受，属增长项 | P3 |

---

### 环节 2：加入购物车

**主流平台做法**：加购即时反馈（角标、飞入动画）；未登录可加购（本地购物车）登录后合并；购物车支持批量移入收藏、凑单提示、降价提醒。

**差异点与不足**：

| 编号 | 差异点 | 现状 | 主流做法 | 影响评估 | 优先级 |
|---|---|---|---|---|---|
| 2.1 | 加购必须登录 | `POST /api/cart` 带 `@RequireLogin`，未登录不能加购 | 京东/淘宝支持游客加购（本地存储），登录后再合并 | 中：未登录用户被挡在转化漏斗之外 | P2 |
| 2.2 | 无加购即时反馈 | 加购成功后直接 `go('/cart')` 跳转购物车页 | 加购后弹层/角标反馈，停留当前页继续逛 | 中：打断浏览节奏，降低连购率 | P2 |
| 2.3 | 无凑单/免邮提示（购物车内） | 免邮门槛只在结算页出现 | 购物车内即提示「再买 X 元免邮」 | 中：错失提高客单价的抓手 | P2 |
| 2.4 | 库存不足时加购静默封顶 | 加购数量按库存封顶，返回最终数量 | 明确提示「已达库存上限」并高亮 | 低：`add` 已返回最终数量，前端可补提示 | P3 |

---

### 环节 3：结算试算（填写订单信息）

**主流平台做法**：省市区三级联动地址选择；默认地址智能选中；支持多收货地址、发票信息、配送时间预约；优惠券智能推荐最优券；满减/满折多种优惠叠加。

**差异点与不足**：

| 编号 | 差异点 | 现状 | 主流做法 | 影响评估 | 优先级 |
|---|---|---|---|---|---|
| 3.1 | 地址为手填文本框 | 省/市/区是三个自由文本框，无级联选择 | 省市区三级联动下拉，地址簿管理 | 高：地址填写体验差，易出错，且无省市区字典校验 | P1 |
| 3.2 | 无最优券自动推荐 | 需用户手动展开券列表选择 | 平台自动计算并默认使用「最优优惠」 | 中：不会选券的用户多付钱，影响体验与口碑 | P2 |
| 3.3 | 无配送时间预约 | 配送方式写死「标准配送 48h」 | 支持配送时效选择、预约时段 | 低：当前体量可接受 | P3 |
| 3.4 | 无发票功能 | 无发票信息填写 | 个人/企业发票是标配 | 低：B 端/企业采购场景缺失 | P3 |
| 3.5 | 优惠形式单一 | 仅满减券一种 | 满减/满折/单品券/平台券叠加 | 中：营销玩法单一，限制促销能力 | P2 |

---

### 环节 4：提交订单（下单）

**主流平台做法**：下单前二次确认；库存锁定与支付超时释放；拆单（不同商家/仓库拆单）；限购校验；风控（防刷单、黑名单）。

**差异点与不足**：

| 编号 | 差异点 | 现状 | 主流做法 | 影响评估 | 优先级 |
|---|---|---|---|---|---|
| 4.1 | 下单即扣库存，取消才回补 | `deductStock` 在下单时直接扣减，非「预占/锁定」 | 主流是下单锁库存，支付超时释放（本项目已有超时关单回补，但属「扣减后回补」而非「锁定」） | 低：本项目已有关单回补机制，语义差异影响有限，但秒杀高并发下「扣减+回补」会有库存波动 | P3 |
| 4.2 | 无拆单 | 一笔订单所有商品单一收货地址、单一物流 | 多商家/多仓自动拆单，各自结算物流 | 中：当前是平台自营+用户发布的混合模式，用户发布商品场景下跨卖家商品无法合并发货 | P2 |
| 4.3 | 无风控 | 无防刷、限购、黑名单、异常下单识别 | 主流有完整风控体系 | 中：防刷单/防恶意下单缺失 | P2 |
| 4.4 | 货到付款无金额/地区限制 | 货到付款（payment=2）无条件可选 | 货到付款通常有地区、金额限制 | 低：演示环境可接受 | P3 |

---

### 环节 5：支付

**主流平台做法**：聚合支付（支付宝/微信/银联/分期）；支付结果异步通知+主动查询双通道对账；支付中台；退款原路退回。

**差异点与不足**：

| 编号 | 差异点 | 现状 | 主流做法 | 影响评估 | 优先级 |
|---|---|---|---|---|---|
| 5.1 | 支付为本地模拟网关 | `mockCallback` 模拟三方回调，无真实扣款 | 接入支付宝/微信真实支付 SDK | **高**：无法真实收款，是「上线」的硬门槛 | P0 |
| 5.2 | 无支付结果主动查询对账 | 仅靠回调推进状态，无主动查询补单 | 回调 + 定时主动查询双通道，防止掉单 | 中：真实接入后掉单会导致「钱付了订单还待付款」 | P1 |
| 5.3 | 无分期/信用支付 | 仅支付宝/微信/银行卡三种，无分期、花呗白条 | 花呗/白条/信用卡分期是主流 | 低：增长项 | P3 |
| 5.4 | 无退款原路退回 | 退款只是改状态，无真实资金退回 | 退款走原支付渠道退回 | 高：与 5.1 同源，真实支付接入后必须配套 | P1 |

---

### 环节 6：支付完成（订单流转与售后）

**主流平台做法**：物流跟踪（快递单号、轨迹查询）；评价晒单；售后退换货完整流程；订单消息通知（App 推送/短信）。

**差异点与不足**：

| 编号 | 差异点 | 现状 | 主流做法 | 影响评估 | 优先级 |
|---|---|---|---|---|---|
| 6.1 | 无物流跟踪 | 发货只改状态，无快递单号、无物流轨迹 | 快递单号 + 轨迹查询 + 签收 | 中：用户无法跟踪包裹，体验缺失 | P2 |
| 6.2 | 无评价入口 | 确认收货后无引导评价 | 确认收货 → 评价 → 晒单闭环 | 中：与 1.2 呼应，评价体系缺失 | P2 |
| 6.3 | 无订单消息通知 | 状态变化无站外通知（仅站内 WebSocket 私信） | App 推送/短信/公众号通知 | 中：用户被动，需主动进站查看 | P2 |
| 6.4 | 自动确认收货后无评价引导 | 自动完成直接终态 | 自动确认后仍引导评价 | 低：与 6.2 合并 | P3 |

## 二、优先级汇总与落地路线

### P0 —— 上线硬门槛（不解决无法真实经营）

| 编号 | 事项 | 说明 |
|---|---|---|
| 5.1 | 接入真实支付 | 支付宝/微信支付 SDK，替换 `mockCallback` 为真实回调 + 验签。订单侧逻辑无需大改（`markPaid` 已幂等），主要工作在支付网关接入与验签 |

### P1 —— 核心体验与功能补全（显著影响转化/可售卖范围）

| 编号 | 事项 | 说明 |
|---|---|---|
| 1.1 | SKU 多规格体系 | 引入 `sku` 表（商品→规格值→SKU 库存/价格），改造商品/购物车/订单明细全链路 |
| 1.2 | 商品评价体系 | 评价表 + 晒图 + 好评率，确认收货后引导评价，详情页展示 |
| 3.1 | 省市区级联地址 | 引入省市区字典，地址改为级联选择，地址簿管理 |
| 5.2 | 支付主动查询对账 | 回调外增加定时主动查询，处理掉单 |
| 5.4 | 退款原路退回 | 真实支付接入后配套退款接口 |

### P2 —— 转化效率与营销能力（中期优化）

| 编号 | 事项 | 说明 |
|---|---|---|
| 1.3 / 3.5 | 优惠券体系增强 | 详情页领券入口、多种优惠类型、结算页最优券推荐 |
| 2.1 | 游客加购 | 本地购物车 + 登录合并 |
| 2.2 | 加购即时反馈 | 加购后弹层/角标，不跳转 |
| 2.3 / 3.2 | 免邮凑单提示 + 最优券 | 购物车内免邮提示，结算页自动选最优券 |
| 4.2 | 拆单 | 多卖家/多仓拆单 |
| 4.3 | 基础风控 | 限购、防刷 |
| 6.1 / 6.2 / 6.3 | 物流跟踪 + 评价 + 通知 | 补齐售后闭环 |

### P3 —— 增长项（有资源再投入）

| 编号 | 事项 | 说明 |
|---|---|---|
| 1.4 / 1.5 / 1.6 | 富文本详情、收藏、个性化推荐 | 内容与增长能力 |
| 3.3 / 3.4 | 配送预约、发票 | 增值能力 |
| 5.3 | 分期/信用支付 | 客单价提升项 |

## 三、落地建议（分阶段）

**第一阶段（打通真实交易）**：P0 + 5.2 + 5.4，先让「真实收款 + 退款 + 对账」闭环可用。

**第二阶段（提升可售卖范围与转化）**：P1 全部，尤其 SKU 多规格（决定能卖什么）与评价（决定转化率）、级联地址（决定下单成功率）。

**第三阶段（营销与增长）**：P2 全部，重点是优惠券体系、游客加购、物流跟踪，形成「引流—转化—复购」闭环。

**第四阶段（增值）**：P3，按业务数据决定优先级。

## 四、附：当前架构对优化的支撑度

现有代码结构对上述优化是**友好的**，多处已预留了扩展点：

1. **金额计算集中在 `PricingService`**：新增多优惠类型、SKU 价格、凑单规则时，只需扩展这一处，试算与下单自动同步。
2. **下单幂等 + 条件扣库存**：`deductStock` / `submitToken` / `transit` 已是并发安全设计，SKU 化后扣库存可平滑迁移到 SKU 维度。
3. **订单状态机 `OrderStatus`**：新增「拆单」「部分退款」等状态时，扩展 `canTransit` 即可。
4. **支付 `markPaid` 幂等**：真实支付接入时，回调与主动查询可安全并发调用而不产生重复推进。

**主要改造点集中在数据模型层**（SKU、评价、物流、省市区字典）与**支付网关接入层**，服务层与前端交互层可复用现有模式。
