东 东华购物 · DhuStore

在线购物系统

项 目 报 告
基于 Spring Boot + MyBatis + Vue 3 的前后端分离商城系统，
涵盖商品、购物车、订单、收货地址、用户发布商品审核与商品多图上传等完整能力。
项目名称：DhuStore（东华购物）
技术架构：B/S · 前后端分离 · RESTful API
开发时间：2026 年 10 月

摘 要

本项目设计并实现了一个面向普通消费者的一站式在线购物系统 —— DhuStore（东华购物）。 系统采用前后端分离架构：后端基于 Spring Boot 4.1.1 与原生 MyBatis 构建 RESTful API， 使用 MySQL 进行数据持久化，通过 JWT 实现无状态身份认证；前端基于 Vue 3 与原生 JavaScript 模块化开发，提供商品浏览、购物车、下单结算、订单管理、个人中心与后台管理等完整交互。

在传统商城功能之上，系统进一步扩展了「用户发布商品」能力：普通用户可以提交商品发布申请， 上传 1~9 张商品图片，由管理员审核；审核通过后，系统在同一个数据库事务内完成 「更新申请状态 + 创建正式商品 + 复制图片关系」，保证数据一致性，并记录商品归属卖家。 商品图片支持阿里云 OSS 存储，未配置 OSS 时自动回退到本地磁盘，兼顾部署成本与可移植性。

后台管理模块提供数据看板、商品管理、分类管理、订单管理与发布申请审核，并支持首页内容运营—— 轮播图、促销位、分类图标与封面、限时秒杀均可自助配置，帮助运营人员掌握销售趋势、处理待发货订单 并完成商品上架审核。系统在安全性方面做了较完整的设计，包括 BCrypt 密码加密、JWT 鉴权、基于角色 的接口权限控制、上传文件的类型与大小校验、UUID 重命名与路径穿越防护。

关键词：在线购物系统；Spring Boot；MyBatis；Vue 3；JWT；商品审核；阿里云 OSS

1项目概述

1.1 项目背景

随着电子商务的普及，在线购物已成为人们日常消费的重要方式。一个完整的购物系统不仅需要 商品展示与交易流程，还需要处理库存、订单状态、用户身份、支付方式以及售后等业务。 本项目在此基础上进一步引入「用户作为卖家发布商品」的 C2C 能力，使平台从单一自营商城 扩展为可以容纳第三方商品的综合性商城。

1.2 建设目标

  • 构建一套结构清晰、分层明确、易于扩展的前后端分离商城系统；
  • 完整实现「浏览 → 加购 → 结算 → 支付 → 发货 → 收货」的购物闭环；
  • 实现用户商品发布申请与管理员审核流程，保证申请数据与正式商品数据隔离；
  • 支持商品多图上传、预览、排序与详情页轮播展示；
  • 提供管理员数据看板与运营工具，提升后台管理效率；
  • 在安全层面落实密码加密、接口鉴权、文件上传校验等机制。

3系统设计

3.1 总体架构

系统采用典型的三层 B/S 架构。浏览器加载 Vue 3 单页应用，前端通过 fetch 调用以 /api 开头的 RESTful 接口；后端在进入 Controller 之前由 JWT 拦截器 完成身份解析与权限校验，随后由 Service 层组织业务与事务，Mapper 层通过 XML 执行 SQL， 最终访问 MySQL 与阿里云 OSS。

层次技术选型理由
后端框架Spring Boot 4.1.1自动配置、生态成熟，快速构建 REST 服务。

4数据库设计

4.1 实体关系

系统共设计 13 张数据表。用户与购物车、地址、订单、发布申请均为一对多关系； 商品与商品图片为一对多；申请与申请图片为一对多。审核通过时，申请图片会被复制为商品图片， 从而在数据库中形成「申请数据」与「正式商品数据」的物理隔离。 此外，banner（轮播）、site_setting（站点配置）与 flash_sale（秒杀位）三张表支撑首页内容运营，均与商品表形成弱引用关系。

5核心业务实现

5.1 购物下单流程

下单是系统中最需要保证一致性的流程。用户在购物车勾选商品后进入结算页，选择收货地址与支付方式， 提交订单时后端在同一个事务内依次完成：校验地址归属、读取勾选商品、逐项扣减库存并增加销量、 写入订单主表与明细表、清除已结算的购物车项。任一商品库存不足都会抛出业务异常并回滚整个事务。

图 5-1 下单与订单状态流转

5.2 商品发布与审核流程

用户提交的商品不会直接写入正式商品表，而是先写入 product_apply 与 product_apply_image。管理员审核通过时，后端在同一个事务内完成三件事： 更新申请状态与审核信息、创建 product 记录（写入 seller_id）、 把申请图片复制到 product_image。这样既保证了「申请通过」与「商品创建」的原子性， 也天然实现了申请数据与正式数据的隔离。

图 5-2 商品发布与审核流程
防重复审核：审核前检查申请状态，只有 status = 0 的申请允许操作， 否则返回业务码 2005（该申请已审核），避免重复生成商品。

5.3 商品多图上传

图片上传采用「前端预校验 + 后端强校验」的双重机制。前端在用户选择文件时立即校验数量、格式与大小， 并调用上传接口即时预览；后端再次校验文件大小、扩展名与 Content-Type，校验通过后使用 UUID 重命名并写入 OSS，返回可访问的 URL。订单、商品详情等场景只保存 URL，不保存二进制数据。

图 5-3 图片上传与校验链路

5.4 身份认证与权限控制

用户登录成功后，后端使用 HS256 算法签发 JWT，载荷包含用户 ID、用户名与角色。前端将 token 保存在 localStorage，之后所有请求通过 Authorization: Bearer <token> 携带。后端拦截器对 /api/** 统一解析 token：若接口标注 @RequireLogin 则强制要求登录；标注 @RequireAdmin 时额外要求角色为 1。当前用户信息通过 ThreadLocal 在请求生命周期内传递，请求结束后统一清理，避免线程复用导致的数据串扰。

5.5 首页内容运营

首页的轮播图、促销位、分类图标与封面、限时秒杀均可在后台自助配置，不再写死在前端代码里。 轮播图存于 banner 表（最多 5 张，超出返回业务码 2011）；两个促销位图片存于 site_setting 键值表；分类图标与 16:9 封面分别存于 category.icon 与 category.cover。所有素材统一通过 POST /api/common/upload 上传， 数据库只保存 URL。未配置素材时，各位置回落到内置占位：轮播显示空白占位、促销位回落到渐变卡片、 分类无封面时回落到按分类色相生成的柔和渐变。

5.6 限时秒杀

秒杀位存于 flash_sale 表，product_id 唯一约束保证同一商品不重复上秒杀位， 最多 8 个，首页按 sort 顺序展示前 4 个。与常规「快照」做法不同，秒杀位只存商品引用， 商品的改价、库存变化、下架都会实时反映到首页，避免数据不一致。重复添加返回业务码 2014、超限返回 2015。前台秒杀数据优先读取后台配置，未配置时回落到「按库存自动取前 4 件」。

7接口设计

7.1 统一响应

所有接口 HTTP 状态码恒为 200，业务结果通过响应体中的 code 区分：

{
  "code": 200,
  "message": "操作成功",
  "data": { ... }
}

前端在 core.js 中统一处理信封：code = 200 时取出 data； code = 401 时清除会话并跳转登录；其余情况抛出包含 code 与 message 的对象，由视图提示。后端由 GlobalExceptionHandler 保证 业务异常、参数校验异常与系统异常都返回同一结构。

8安全设计

8.1 认证与授权

  • 密码安全：注册时使用 BCrypt 对密码加盐哈希，数据库中不保存明文；登录时使用 matches 校验，接口响应中不返回密码字段。
  • 无状态认证：JWT 使用 HS256 签名，密钥长度不少于 32 字节，token 默认 24 小时过期。
  • 接口级权限：@RequireLogin 与 @RequireAdmin 由拦截器统一执行， 不依赖前端隐藏按钮，普通用户无法通过直接调用接口越权。
  • 上下文隔离：用户信息存放在 ThreadLocal，请求结束即清理，防止线程复用串号。

8.2 文件上传安全

  • 限制单文件 5MB、单请求 50MB（Spring Multipart 配置 + 业务校验双重限制）；
  • 白名单校验扩展名（jpg / jpeg / png / webp）与 Content-Type，不信任前端 accept；
  • 文件名完全由服务端生成（UUID），避免恶意文件名与覆盖攻击；
  • 本地存储时校验目标路径必须位于上传根目录内，防止路径穿越；
  • 上传接口要求登录，未登录请求返回 401。

8.3 业务与数据安全

  • 越权防护：地址、购物车、订单的查询与修改均附带 user_id 条件， 用户只能操作自己的数据；订单查询还会校验归属。
  • 库存并发：扣减库存使用 WHERE stock >= #{quantity} 的条件更新， 通过影响行数判断是否成功，避免超卖。
  • 事务一致性：下单、取消订单、审核通过均使用 @Transactional。
  • XSS 防护：商品详情按纯文本渲染（不使用 v-html），避免后台录入内容注入脚本。
  • 敏感配置：数据库密码、JWT 密钥与 OSS AccessKey 存放于被 gitignore 的本地配置文件， 仓库中仅保留环境变量占位符。

10总结与展望

10.1 项目成果

  • 完成了一个可运行、可演示的前后端分离在线购物系统，覆盖商品、购物车、订单、地址等核心交易链路；
  • 实现了用户发布商品与管理员审核的 C2C 扩展，并通过事务与状态校验保证申请与正式商品的数据一致性；
  • 实现了商品多图上传、预览与详情页展示，接入阿里云 OSS 并支持本地存储回退；
  • 实现了首页内容运营能力：轮播图、促销位、分类图标与封面、限时秒杀均可在后台自助配置；
  • 完成了管理员数据看板、商品管理、分类管理、订单管理与发布申请审核等运营能力；
  • 建立了全站统一的线性 SVG 图标体系与响应式布局，桌面端与移动端均可正常访问；
  • 形成了统一响应、统一异常、统一鉴权的后端基础设施，后续新增模块成本较低。

10.2 存在的不足

  • 消息提醒采用登录与操作后的拉取刷新，尚未实现 WebSocket 实时推送；
  • 商品图片排序按上传顺序，暂未支持拖拽调整；
  • 商品与申请列表使用 LIKE 模糊查询，数据量增大后需要引入全文检索；
  • 下单成功后的「支付」为模拟状态流转，尚未接入真实支付渠道；
  • 秒杀位无独立秒杀价与限时结束时间，仅做展示位编排；
  • 单机部署，未引入缓存与消息队列；移动端页头导航尚未收纳为抽屉菜单；
  • 缺少自动化测试与持续集成流程。

10.3 后续规划

  1. 卖家中心：基于 seller_id 提供「我的商品」「销售统计」「上下架」能力；
  2. 实时通知：使用 WebSocket 或 SSE 推送新订单、发货、审核结果；
  3. 交易增强：订单超时自动取消、退款流程、优惠券、运费模板；
  4. 性能优化：引入 Redis 缓存热点商品与验证码，图片接入 CDN；
  5. 工程质量：补充单元测试与接口测试，接入 CI 自动构建与部署；
  6. 运维能力：接入日志聚合、监控告警与健康检查。
结语：本项目从需求分析、数据库设计到接口实现与前端交互，完整走通了一个电商系统的核心闭环， 并在用户发布商品、审核事务、多图存储等环节进行了较深入的设计实践。系统结构清晰、层次分明， 为后续扩展为真正的多卖家商城奠定了基础。
