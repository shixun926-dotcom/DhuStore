# DhuStore 引入 Redis 可行性分析

> 版本：V1.0 ｜ 编写日期：2026-10-28
> 范围：评估在当前项目引入 Redis 作为缓存的可行性与利弊
> 结论先行：**当前阶段（单机部署、小体量）不建议急于全面引入 Redis，建议按「热点缓存 → 计数 → 会话」分阶段、按需引入，并优先用 Spring Cache 抽象层解耦，避免过早绑定。**

---

## 一、结论与核心判断

**总体判断：可行，但非当前刚需。** 本项目当前是单机部署、数据量小、流量低的教学/演示型项目，MySQL 8 本身即可承载。引入 Redis 的**真实收益只有在出现明确瓶颈后才成立**，过早引入会带来缓存一致性、内存成本、运维复杂度等净负担。

**分阶段结论：**

| 阶段 | 是否引入 | 依据 |
|---|---|---|
| 现在（单机、小流量） | **暂不引入** | 无明确瓶颈，MySQL 足够；引入是负收益 |
| 出现热点读瓶颈后 | **阶段一：热点数据缓存** | 首页/分类/秒杀/促销位是最高频只读接口 |
| 需要多实例/高并发计数 | **阶段二：计数与会话** | 销量/关注/粉丝计数、WebSocket 在线表 |
| 生产化、需水平扩展 | **阶段三：会话与分布式能力** | 替代单机 `ConcurrentHashMap` 在线表、分布式锁 |

## 二、适合使用 Redis 的场景与数据（结合本项目实际）

### 2.1 热点只读数据（最优先，收益最明确）

| 数据 | 现状 | Redis 方案 | 收益 |
|---|---|---|---|
| 首页轮播 `banner` | 每次请求查库 | 缓存列表，后台更新时失效 | 首页是最高频入口，QPS 最高 |
| 分类树 `category` | 每次查库 + 每个分类 `COUNT(*)` 算商品数 | 缓存分类树与商品数 | 分类商品数是子查询，每次首页都算 |
| 秒杀位 `flash_sale` | 每次查库（JOIN product） | 缓存秒杀位配置 | 秒杀位是首页核心模块 |
| 促销位 `site_setting` | 每次查库 | 缓存键值对 | 低频率变更、高频读取 |
| 商品详情 `product` | 每次查库 | 缓存商品主数据（注意与库存/销量分离） | 详情页是转化核心 |

**关键点**：这五类都是「读多写少」数据，最适合缓存，且是**公开接口**（无需鉴权、可共享缓存、可做 CDN 之外的服务器缓存）。

### 2.2 计数与统计（次优先，需谨慎设计）

| 数据 | 现状 | 问题 | Redis 方案 |
|---|---|---|---|
| 商品销量 `sales` | `deductStock` 时 `sales = sales + qty` 同步写库 | 高频写放大，与库存联动耦合 | `INCR` 异步累加，定时刷回 DB |
| 关注数/粉丝数 `follower_count` | 每次 `SELECT COUNT(*)` 子查询 | 关注列表/个人页反复实时聚合 | Redis 计数 + 定期校准 |
| 未读消息数 | 每次 `COUNT(*)` | 会话列表每行都统计 | `INCR`/`DECR` 维护未读计数 |
| 后台看板统计 | 实时 `SUM/COUNT/GROUP BY` 聚合 | 大时间范围聚合慢 | 缓存聚合结果（TTL 短） |

**关键风险**：销量、关注数这类计数若缓存，必须处理**缓存与 DB 不一致**问题（详见第三节）。

### 2.3 会话与在线状态（多实例才需要）

| 数据 | 现状 | Redis 方案 |
|---|---|---|
| WebSocket 在线表 | `ChatSessionRegistry` 单机 `ConcurrentHashMap` | Redis pub/sub + 在线集合 |
| 登录 token 黑名单 | JWT 无状态，token 无法主动失效 | Redis 存黑名单/白名单，实现登出即失效 |

**关键点**：`ChatSessionRegistry` 代码注释已明确「多实例部署需替换为 Redis 广播」，这是**唯一在代码里预留了 Redis 指向**的地方。单机部署时现有实现完全够用，无需引入。

### 2.4 其他可选场景（当前不推荐）

| 场景 | 说明 | 结论 |
|---|---|---|
| 分布式锁 | 下单幂等/扣库存已有 DB 层保证，单机无需 | 多实例后再考虑 |
| 限流/防刷 | 当前无风控需求 | 与风控一起做 |
| 验证码/短 token | 当前无此功能 | 未来有短信/验证码时引入 |

## 三、对现有架构和性能的影响

### 3.1 正面影响

1. **降低热点读的 DB 压力**：首页/分类/秒杀这类高频只读接口，缓存后 DB 查询次数可下降一个数量级。
2. **减少实时聚合**：分类商品数、关注数、未读数的 `COUNT(*)` 子查询可被缓存/计数替代，列表接口响应更快。
3. **为水平扩展铺路**：`ChatSessionRegistry` 的单机内存在线表是当前架构中**唯一的多实例扩展障碍**，Redis 是标准解法。

### 3.2 架构改动点

| 层 | 改动 | 复杂度 |
|---|---|---|
| 依赖 | 新增 `spring-boot-starter-data-redis` + `commons-pool2` | 低 |
| 配置 | `application.properties` 加 Redis 连接配置 | 低 |
| 抽象层 | **强烈建议引入 Spring Cache（`@Cacheable` 等）**，先与具体缓存实现解耦 | 中 |
| Service 层 | 在 `ProductService`/`CategoryService`/`SiteSettingService` 等方法加缓存注解 + 失效逻辑 | 中 |
| 基础设施 | 本机需安装/启动 Redis（Windows 下无官方版，需 WSL/Docker/第三方移植） | **需注意** |

### 3.3 性能影响的双面性

- **读路径加速**：缓存命中时，热点接口从「DB 往返」降到「Redis 往返」，延迟可降一个量级。
- **写路径新增负担**：所有缓存失效操作成为写路径的额外步骤，若失效逻辑设计不当，会引入新的延迟与失败点。
- **序列化开销**：对象缓存需选序列化方式（JSON/Protobuf），有轻微 CPU 开销。

## 四、可能的风险（重点）

### 4.1 缓存一致性（最大风险）

本项目**库存与销量是强一致数据**（`deductStock` 里 `stock` 和 `sales` 联动），一旦缓存商品数据，极易出现：

- **缓存了旧价格/旧库存**：商品价格改了、库存扣了，缓存未失效，用户看到过期数据下单失败。
- **销量计数漂移**：异步累加若进程崩溃，Redis 计数与 DB 销量永久不一致。

**缓解方案**：
- 库存、销量等强一致字段**不进缓存**，只缓存商品主数据（名称/图片/描述）等弱一致字段；
- 采用 **Cache-Aside（旁路缓存）** 模式：读时加载、写时删除（而非更新），配合 TTL 兜底；
- 计数类用「Redis 累加 + 定时/阈值刷回 DB + 定期全量校准」三段式，接受短暂最终一致。

### 4.2 内存成本

- 商品详情含 `detail`（富文本）与 `sub_images`，单条可能数 KB～数十 KB，缓存数千商品即占用数十 MB。
- **必须设 TTL + 容量上限（maxmemory）+ 淘汰策略（allkeys-lru）**，否则内存失控。

### 4.3 运维复杂度

- **新增一个基础设施组件**：Redis 需要独立部署、监控、备份（RDB/AOF）、主从/哨兵/集群（高可用时）。
- **Windows 环境不友好**：Redis 官方不提供 Windows 版，本机（win32）需 WSL/Docker/第三方移植（如 Memurai/tporadowski），或远程 Redis。
- **故障域扩大**：Redis 宕机会影响依赖它的接口，需设计降级（缓存穿透/击穿/雪崩防护）与熔断。

### 4.4 缓存穿透 / 击穿 / 雪崩（引入后的经典问题）

| 问题 | 场景 | 本项目易发点 |
|---|---|---|
| 穿透 | 查不存在的 key | 不存在的商品 id 反复查 DB |
| 击穿 | 热点 key 过期瞬间大量请求 | 秒杀位、爆款商品详情 |
| 雪崩 | 大量 key 同时过期 | 首页各模块缓存同一时刻过期 |

均需用「空值缓存 + 互斥锁 + TTL 随机化」等标准手段防护，这是引入 Redis 后的**持续成本**。

## 五、分阶段引入建议

### 阶段 0：现在 —— 不引入，先做架构解耦准备

- **不引入 Redis**，保持现状，MySQL 足够。
- 可预先做一件事：**引入 Spring Cache 抽象**（`spring-boot-starter-cache`），先用 `ConcurrentMapCache`（本地缓存）或 `Caffeine` 做本地缓存，验证缓存逻辑与失效设计，**后续切换 Redis 只改一个配置**。
- 这一步风险低、收益可验证，是「为 Redis 铺路」的最优前置动作。

### 阶段 1：出现热点读瓶颈后 —— 热点数据缓存

- 目标：首页轮播、分类树、秒杀位、促销位、商品主数据。
- 方案：`@Cacheable` + Cache-Aside，写时删除 + TTL 兜底。
- 强一致字段（库存/销量）**严格不进缓存**。

### 阶段 2：高并发计数需求 —— 计数与会话

- 目标：销量、关注/粉丝数、未读数。
- 方案：Redis `INCR` 累加 + 定时刷回 DB + 定期校准。
- 前提：已确认这些计数成为性能瓶颈（否则不划算）。

### 阶段 3：多实例 / 水平扩展 —— 分布式能力

- 目标：`ChatSessionRegistry` 替换为 Redis pub/sub；分布式锁；token 黑名单。
- 前提：**必须**，否则 WebSocket 消息在多实例间无法投递。

## 六、替代方案对比

| 方案 | 适用场景 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **维持现状（MySQL）** | 当前小体量 | 零成本、零风险、架构简单 | 热点读/计数成为瓶颈后不可扩展 | ✅ **当前推荐** |
| **本地缓存 Caffeine** | 单机、热点读瓶颈 | 无需额外组件、极快、易用 | 单机内存、多实例不共享、进程重启丢失 | ✅ **阶段 1 首选** |
| **Redis（远程/容器）** | 多实例、需共享缓存/计数/会话 | 共享、持久化、丰富数据结构 | 运维成本、一致性、网络延迟 | ⭕ 阶段 2/3 按需 |
| **Spring Cache + 可插拔 provider** | 想要渐进、不绑定 | 抽象层解耦，Caffeine↔Redis 无缝切换 | 需先设计缓存 key 与失效 | ✅ **推荐作为骨架** |
| **直接上 Redis（跳步）** | 明确已有多实例/高并发 | 一步到位 | 过早引入净负收益 | ❌ 不推荐 |

**核心建议**：采用 **「Spring Cache 抽象 + Caffeine 起步」** 的渐进路线。先用本地缓存解决单机热点读，同时把缓存逻辑抽象好；当且仅当出现「多实例共享」或「计数成为瓶颈」时，把 provider 切换为 Redis，代码层几乎零改动。

## 七、关键决策清单（供后续评审）

1. **是否已出现可量化的性能瓶颈？** —— 若没有，不要为了「用 Redis 而用 Redis」。
2. **强一致数据（库存/销量）与弱一致数据（商品主数据）是否已分离？** —— 这是缓存设计的第一原则。
3. **是否接受最终一致？** —— 计数类缓存必然牺牲强一致，需业务确认。
4. **本机 Windows 环境如何跑 Redis？** —— 需 WSL/Docker/远程，这是当前落地的实际障碍。
5. **是否准备接受一个额外基础设施的运维负担？** —— 监控、备份、高可用、故障降级。

## 附：本项目与 Redis 高契合度的唯一硬性指征

代码中 `ChatSessionRegistry` 已明确注释：

> 「单机内存实现，多实例部署需替换为 Redis 广播」

这意味着一旦项目走向**多实例水平扩展**，Redis 是**不可回避**的依赖（至少用于 WebSocket 会话广播与在线状态共享）。除此之外，其余场景均属于「锦上添花」，应按需、分阶段引入，而非当前阶段必须。
